Part A: Broken Banking Transaction UI

You are given a simplified Angular component used in production. It has multiple bugs and performance issues.

Question 1

Identify all issues that could break or degrade production performance.

Question 2

Rewrite or describe how you would fix:

  1. State handling issue
  2. Subscription issue (if any)
  3. Performance issue
  4. Template issue (if applicable)
transactions.component.ts
@Component({
  selector: 'app-transactions',
  template: `
    <input (input)="onSearch($event)" placeholder="Search" />

    <div *ngFor="let t of filteredTransactions">
      {{ '{' }}{{ '{' }} t.category {{ '}' }}{{ '}' }} - {{ '{' }}{{ '{' }} t.amount {{ '}' }}{{ '}' }}
    </div>
  `
})
export class TransactionsComponent {
  transactions = [];
  filteredTransactions = [];

  ngOnInit() {
    this.transactionService.getTransactions().subscribe(data => {
      this.transactions = data;
      this.filteredTransactions = data;
    });
  }

  onSearch(event: any) {
    const value = event.target.value;

    this.filteredTransactions = this.transactions.filter(t =>
      t.category.includes(value)
    );
  }
}

Part A — Question 1: Issues identified

  • Missing service injection: The transactionService is never injected into the component. Calling getTransactions() will fail because the component has no reference to the service.
  • Unsafe and case-sensitive search: t.category.includes(value) can throw if category is null or undefined. It is also case-sensitive, so searching for "food" will not match "Food". Normalize the values and handle missing categories.
  • Duplicate state management: The component maintains both transactions and filteredTransactions, although the filtered list is derived from the original list. Keep one source of truth and derive the filtered results.
  • Subscription management: The component subscribes manually without cleanup. HTTP observables normally complete automatically, but long-lived observables could cause memory leaks. Use the async pipe or takeUntilDestroyed().
  • Performance: Filtering scans the list on each keystroke, and the repeated rows have no tracking key. This is usually fine for small lists, but large histories may benefit from debouncing, pagination, or server-side filtering.
  • Template and user experience: The input has no accessible label, and the template provides no loading, error, or empty states. Amounts are not formatted as currency.

Part A — Question 2: Recommended fixes

2a. State handling

Keep transactions and the search query as the source of truth, and derive the filtered results instead of storing a second array. Normalize search text and handle missing categories safely.

2b. Subscription

A one-time HttpClient request completes automatically. For a long-lived observable, use takeUntilDestroyed() or the async pipe. Handle request errors and show the loading state.

2c. Performance

Track rows by a stable transaction ID. Filtering a modest list on each keystroke is usually fine; debounce or use pagination/server-side filtering if list size or measured performance calls for it.

2d. Template

Add an accessible search label and loading, error, and empty states. Import NgFor (or use @for with a tracking key) and format amounts with Angular's currency pipe.

Example implementation for Question 2

transactions.component.ts
import { Component, DestroyRef, computed, inject, signal } from '@angular/core';
import { CurrencyPipe, NgFor, NgIf } from '@angular/common';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { TransactionService } from './transaction.service';

interface Transaction {
  id: string;
  category: string | null;
  amount: number;
}

@Component({
  selector: 'app-transactions',
  standalone: true,
  imports: [NgFor, NgIf, CurrencyPipe],
  template: `
    <label for="transaction-search">Search transactions</label>
    <input id="transaction-search" type="search"
      (input)="onSearch($event)" />

    <p *ngIf="loading()">Loading transactions...</p>
    <p *ngIf="error()" role="alert">{{ '{' }}{{ '{' }} error() {{ '}' }}{{ '}' }}</p>
    <p *ngIf="!loading() && !error() && filteredTransactions().length === 0">
      No transactions found.
    </p>

    <div *ngFor="let transaction of filteredTransactions(); trackBy: trackTransaction">
      {{ '{' }}{{ '{' }} transaction.category || 'Uncategorized' {{ '}' }}{{ '}' }} -
      {{ '{' }}{{ '{' }} transaction.amount | currency {{ '}' }}{{ '}' }}
    </div>
  `
})
export class TransactionsComponent {
  private readonly destroyRef = inject(DestroyRef);
  private readonly transactionService = inject(TransactionService);

  readonly transactions = signal<Transaction[]>([]);
  readonly query = signal('');
  readonly loading = signal(true);
  readonly error = signal(false);

  readonly filteredTransactions = computed(() => {
    const term = this.query().trim().toLocaleLowerCase();
    return this.transactions().filter(transaction =>
      (transaction.category ?? '').toLocaleLowerCase().includes(term)
    );
  });

  ngOnInit(): void {
    this.transactionService.getTransactions()
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe({
        next: data => {
          this.transactions.set(data);
          this.loading.set(false);
        },
        error: () => {
          this.error.set(true);
          this.loading.set(false);
        }
      });
  }

  onSearch(event: Event): void {
    this.query.set((event.target as HTMLInputElement).value);
  }

  trackTransaction(_index: number, transaction: Transaction): string {
    return transaction.id;
  }
}

Part B: Multi-Bank Custom UI Engine

You are building a system where 10 or more banks use the same Angular frontend. Each bank has different UI layouts, onboarding flows, and validation rules. You cannot rebuild per bank; everything must be runtime configurable.

Questions

How would you design the frontend so that:

  1. One codebase supports all banks
  2. UI changes dynamically per bank
  3. Features can be enabled or disabled per bank

1. One codebase for all banks

Use one Angular app for every bank. When the app starts, load that bank's settings, such as its theme, layout, and enabled features.

bank-config.ts
interface BankConfig {
  tenantId: string;
  primaryColor: string;
  layout: string[];
  features: Record<string, boolean>;
}

const bankConfig = await loadBankConfig(bankId);
applyBankConfig(bankConfig);

2. UI changes dynamically per bank

Let each bank's settings choose the order of existing page sections and onboarding steps. The app maps those names to components it already knows how to display.

layout-registry.ts
const widgets = {
  'account-summary': AccountSummaryComponent,
  transactions: TransactionsComponent
};

const layout = ['account-summary', 'transactions'];
render(layout.map(key => widgets[key]));

Onboarding steps and field rules can also be bank-specific settings. The app maps each setting to a shared step component or validator:

bank-flow-config.ts
const onboardingSteps = [
  'personal-details',
  'identity-check'
];

const validationRules = {
  accountNumber: ['required', 'account-number']
};

const stepComponents = {
  'personal-details': PersonalDetailsComponent,
  'identity-check': IdentityCheckComponent
};

const validators = {
  required: requiredValidator,
  'account-number': accountNumberValidator
};

3. Per-bank feature controls

Keep feature switches in the bank settings and check them before showing a feature. The server should also check that the user is allowed to perform the action.

feature-service.ts
function isEnabled(name: string): boolean {
  return bankConfig.features[name] ?? false;
}

if (isEnabled('transfers')) {
  showTransfersLink();
}
